# WooriLog 기획 초안

## 현재 개발 범위 — SQLite 첫 버전 확정

- 회원가입 없이 사용하며 기기 사용자를 가족관리자로 취급한다.
- 가족과 건강 기록은 `expo-sqlite`로 Android 기기에 저장한다. 네트워크와 개발 PC 없이 데이터 기능이 동작한다.
- 이메일·비밀번호, Google 로그인, 초대 코드, 사용자별 권한, 기기 간 공유 및 Supabase 연동은 보류한다.
- 아래 가족 공유·인증 요구사항은 Supabase 단계의 목표로 보존하며 현재 버전에 적용하지 않는다.
- 추후 Supabase 전환 시 개발 데이터는 유실되어도 된다. 현재 백업·복원 및 데이터 이전 도구는 만들지 않는다.
- 화면과 비동기 저장·조회 함수를 분리하고, 고유 ID·가족 연결·DB 버전을 관리한다.

### 이번 구축 작업

- 목적: Expo 실행 기반과 SQLite 영속 저장을 구축하고 필수 기록 순서를 연결한다.
- 범위: Android용 Expo/TypeScript 프로젝트, 가족 구성원 관리, 건강 기록 저장·조회·수정·삭제 함수, 기록 기반 홈 요약, 가족 선택 → 몸 영역 선택 → 상세 입력 진입.
- 상세 폼 디자인과 항목은 이후 확정한다. 이번에는 저장 검증용 증상 입력만 최소 구성한다. 발병 묶음·경과·진단·리포트 고도화는 이후 설계한다.
- 기록 없는 구성원은 삭제하고, 기록이 있는 구성원은 보관 처리하여 기존 기록을 유지한다. 보관한 구성원은 새 기록 대상에서 제외한다.
- 검증: 타입 검사, Expo 패키지 호환성, Android JS 번들 생성, 실제 SQLite를 이용한 데이터 작업·제약·재실행 보존 테스트. APK/AAB 빌드 및 배포는 수행하지 않는다.

## 제품 목표와 확정된 요구사항

가족의 건강 기록을 한곳에 모아 자주 아픈 부위, 최근 증상이나 질병, 과거의 유사한 경험을 빠르게 확인한다.

- 초기 관리자는 아빠이며 가족 구성원을 등록하고 기록한다.
- 매일 또는 건강 관련 이벤트가 발생했을 때 가족별로 기록한다.
- 자주 아픈 부위와 최근 아픈 부위 또는 질병을 조회한다.
- 기록을 시각화하여 가족 구성원의 몸 상태를 돌아볼 수 있는 리포트를 제공한다.
- 같은 질병을 과거에 언제 겪었고 어떻게 대처했는지 연결하여 참고할 수 있게 한다.
- 지원 플랫폼은 Android 전용이다.
- 이메일·비밀번호 회원가입/로그인과 Google 로그인을 지원한다.
- 회원가입 시 가족을 설정하거나 초대 코드를 입력하여 가족에 참여한다. 참여한 사용자는 로그인 후 가족 리포트를 볼 수 있다. 신규 가족 생성과 초대 참여의 상세 화면 순서는 추후 확정한다.
- 가족관리자는 가족당 1인이다. 관리자는 초대한 사용자의 건강 기록 등록·수정·삭제를 묶은 편집 권한을 부여하거나 회수할 수 있다.

### 가족과 권한 — Supabase 단계에 적용

- 가족 리포트는 초대받아 가입한 가족 사용자가 각자 기기에서 조회한다.
- 초대받은 사용자의 기본 권한은 조회 전용이다. 관리자는 건강 기록 등록·수정·삭제를 묶은 하나의 편집 권한을 부여하거나 회수한다.
- 편집 사용자는 같은 가족 그룹 안에서 건강 기록을 등록하고, 다른 사용자가 작성한 건강 기록도 수정·삭제할 수 있다.
- 가족 구성원 추가·삭제와 사용자 초대는 관리자만 가능하다. 권한 관리도 관리자만 가능하다.
- 기존 구성원의 정보 수정은 앞서 결정한 동일한 편집 권한을 유지한다. 구성원 추가·삭제와 정보 수정은 별도 작업으로 구분한다.
- 계정 하나는 가족 그룹 하나에만 참여한다.
- 사용자는 자신이 참여한 가족 그룹의 데이터만 조회할 수 있고, 편집 권한도 해당 그룹 안에서만 유효하다. 서로 다른 가족 그룹 간 조회·수정은 허용하지 않는다.
- 초기 초대 방식은 초대 코드 입력이다. 초대 코드는 로그인 사용자의 가족 접근 권한을 부여하기 위한 것이며, 기록 대상 구성원의 계정을 만드는 절차가 아니다.
- 건강 기록 대상인 가족 구성원은 로그인 계정과 별도 데이터다. 계정 없는 아이도 등록할 수 있고 구성원 정보는 수정·편집할 수 있다. 계정과 구성원의 일대일 연결은 필수로 요구하지 않는다.
- 가족 건강 기록의 저장·공유 및 권한 확인을 위한 서버가 필요하다. 서비스와 동기화 방식은 아직 선정하지 않았다.
- 구현 시 가족 접근 및 쓰기 권한은 화면 표시뿐 아니라 서버에서도 확인한다.

## 기획 방향

사용자는 전체 기획 방향에 동의했다. 아래 필수 입력 흐름은 확정 요구사항이며, 세부 제안과 미결정 사항은 사용자에게 질문하고 답변을 받은 뒤 결정한다.

### 핵심 흐름

로그인과 가족 설정 또는 초대 수락이 완료된 사용자의 핵심 흐름:

앱 실행 → 홈(리포트) → 기록 시작 → 가족 구성원 선택 → 아픈 영역 선택 → 아픈 내용 상세 폼.

조회 전용 사용자의 기록 진입 표시 방식은 추후 결정한다.

### 필수 입력 경험

- 기록 방식은 앱의 핵심 강점으로 구현한다. 가족과 건강이라는 컨셉에 맞는 단계별 선택 인터페이스를 제공한다.
- 앱 실행 후 홈은 리포트 화면이다. 홈에서 기록 시작으로 진입한다.
- 기록 시작 후 가족 구성원을 먼저 선택하고, 다음 단계에서 아픈 영역을 선택한다.
- 아픈 영역은 한 화면의 몸 그림에서 머리, 몸통, 팔다리의 3개 그룹으로 선택한다. 가슴·배는 몸통에 포함하고 팔·다리는 하나의 팔다리 그룹으로 취급한다.
- 세 그룹을 서로 다른 색상으로 구분하고, 몸 그림의 해당 영역을 눌러 선택한다. 구체적인 색상과 선택 상태 표현은 미정이다.
- 선택한 가족과 영역을 상세 폼에 전달한다.
- 아픈 내용 상세는 폼 방식으로 구성하되, 세부 항목과 상세 UI는 앱 기반 구성 후 작업한다.
- 한 번의 기록에서 머리·몸통·팔다리 중 하나의 영역만 선택한다.

### 기록 구조

- 사용자 계정: 이메일·비밀번호 또는 Google로 로그인하는 사용자.
- 가족 접근 정보: 사용자 계정이 참여한 하나의 가족과 관리자·조회·편집 권한. 관리자 역할은 가족당 1인이다. 가족 참여가 완료된 계정은 다른 가족에 중복 가입할 수 없다.
- 가족 구성원: 건강 기록의 대상인 별도 프로필 데이터. 표시 이름과 선택적 관계·프로필 정보로 구성하며 로그인 계정 없이도 등록·편집할 수 있다.
- 건강 기록: 발생 일시, 부위, 증상, 선택적 질병명, 불편한 정도, 메모.
- 경과 기록: 동일한 아픔에 대한 후속 상태, 병원 방문, 당시 대처와 이후 변화.
- 아픔 묶음: 한 번 시작된 증상이나 질병의 경과를 연결하는 단위. 여러 날짜에 쓴 기록을 별개의 발병으로 중복 집계하지 않는다.
- 사용자 입력 질병명과 진단받았다고 기재한 질병명은 구분한다. 세부 입력 방식은 추후 결정한다.

### 주요 화면

1. 홈(리포트): 앱의 시작 화면. 가족별 최근 기록과 몸 상태 요약, 기록 시작 진입점.
2. 기록 단계 화면: 가족 구성원 선택 → 아픈 영역 선택 → 아픈 내용 상세 폼.
3. 구성원 건강 이력: 날짜별 기록, 검색·필터, 상세 경과.
4. 몸 상태 리포트: 기간별 부위 분포, 아픔 발생 횟수, 최근 기록.
5. 관련 과거 기록: 같은 질병명 또는 유사한 부위·증상으로 찾은 과거 기록과 대처 과정.
6. 가입·가족 설정·초대 수락: 로그인 및 가족 참여 흐름. 세부 순서는 추후 확정한다.
7. 가족 관리: 관리자가 기록 대상 구성원을 추가·삭제하고 사용자 초대 코드와 편집 권한을 관리한다. 기존 구성원의 정보 수정에는 편집 권한을 적용한다.

### 리포트 및 과거 기록 연결 원칙

- 리포트는 입력된 기록의 요약이며, 기록이 없는 부위를 건강하다고 판정하지 않는다.
- 기록한 횟수와 아픔이 발생한 횟수를 구분하여 표시한다.
- 몸 그림의 부위별 강조와 텍스트 목록을 함께 제공하는 방안을 검토한다.
- 같은 질병명과 유사 증상은 서로 구분하여 관련 기록을 표시한다.
- 과거의 대처와 이후 변화를 보여주되 해당 대처가 회복의 원인이라고 단정하지 않는다.
- 자동 진단이나 치료 추천은 현재 요청 범위에 포함하지 않는다.

## 기술 방향

- Expo, React Native, TypeScript, Expo Router, expo-sqlite를 사용한다. 몸 그림은 react-native-svg로 구현한다.
- Android 전용으로 먼저 SQLite 저장을 구현한다. 후속 백엔드는 Supabase로 정하고 인증·공유·서버 권한 구현은 보류한다.
- 시각화 라이브러리는 몸 그림과 통계의 구체적인 표현을 정한 뒤 선정한다.
- 초기화 시점에 Expo SDK와 라이브러리 호환성을 확인하고 버전을 고정한다.

## 다음 결정 사항

1. 보관한 구성원의 복원 UI와 기록 상세 폼 항목.
2. 매일의 건강 기록에 아프지 않은 날의 상태도 포함하는지.
3. 기록 필수 항목, 아픔 시작·종료 및 과거 기록 연결 방식. 상세 폼은 앱 기반 구성 후 결정한다.
4. Supabase 전환 시 서버 권한·오프라인 동작·동기화 방식. 첫 버전은 SQLite이고 개발 데이터 이전은 요구하지 않는다.
5. 저장 후 이동할 화면, 단계 이동 시 입력 보존 및 중단 처리 방식.
6. 초대 코드 만료·취소·사용 횟수, 가족 탈퇴·제외, 관리자 위임.

## 제품 전체 검증 계획 — 보류 기능은 해당 구현 단계에서 검증

- 가족 A에 작성한 기록이 가족 B의 이력에 섞이지 않는지 확인한다.
- 앱 실행 시 홈 리포트가 표시되고, 기록 시작 → 가족 구성원 → 아픈 영역 → 상세 폼 순서로 이동하는지 확인한다.
- 선택한 가족과 영역이 상세 폼에 정확하게 전달되는지 확인한다.
- 한 기록에서 영역이 하나만 선택되고, 다른 영역 선택 시 기존 선택이 교체되는지 확인한다.
- 관리자가 로그인 계정 없는 구성원을 등록하고, 관리자 또는 편집 사용자가 해당 구성원의 건강 기록을 작성할 수 있는지 확인한다.
- 구성원의 프로필 정보를 수정해도 기존 건강 기록의 연결이 유지되는지 확인한다.
- 이메일·비밀번호 및 Google 로그인, 초대 코드로 가족 참여, 기본 조회 권한과 통합 편집 권한을 각각 확인한다.
- 몸 그림의 머리·몸통·팔다리가 색상으로 구분되고, 좌우 팔과 다리가 모두 팔다리 그룹으로 선택되는지 확인한다.
- 초대 수락과 로그인 후 해당 가족 리포트에 접근하고 다른 가족의 데이터에는 접근할 수 없는지 확인한다.
- 같은 가족의 편집 사용자는 건강 기록 등록 및 다른 작성자의 기록 수정·삭제를 할 수 있고, 조회 사용자는 해당 작업을 할 수 없는지 확인한다.
- 편집 사용자도 가족 구성원 추가·삭제, 사용자 초대, 권한 변경은 할 수 없고 서버에서도 해당 요청을 거부하는지 확인한다.
- 다른 가족 그룹의 식별자로 직접 요청해도 서버가 조회·수정을 거부하는지 확인한다.
- 이미 가족에 참여한 계정의 다른 가족 생성·초대 참여가 거부되는지 확인한다.
- 가족당 관리자가 1인인지 확인하고, 권한 회수 후 서버가 해당 사용자의 쓰기 요청을 거부하는지 확인한다.
- 발생 일시 기준으로 최근 기록을 정확하게 찾는지 확인한다.
- 동일한 아픔의 경과를 여러 번 작성해도 발병 횟수가 늘어나지 않는지 확인한다.
- 기간·부위·증상·질병 필터와 리포트 집계가 원본 기록과 일치하는지 확인한다.
- 과거 기록에서 당시 대처와 이후 경과까지 이동할 수 있는지 확인한다.
- 앱 재실행 후 기록 보존과 가족 사용자 간 데이터 동기화를 확인한다.

### SQLite 기반 구축 결과

- Expo SDK 57 / React Native 0.86.3 / React 19.2.3 / TypeScript / Expo Router / expo-sqlite를 설치하고 npm 잠금 파일을 생성했다.
